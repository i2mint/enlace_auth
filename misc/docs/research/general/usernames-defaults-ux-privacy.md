# Usernames on a multi-app platform: default generation, the choose-your-handle UI, and privacy

Date: 2026-11-27. Scope: the account's private identifier is the verified email; the public handle is a separate, unique, case-insensitive name used by every app on the platform. This report covers default handle generation, the first-run and availability-check UI, and the privacy and GDPR side. Canonicalisation rules (confusables, Unicode profiles) are only touched where they constrain the defaults.

## Summary

A handle is public by design, so its existence can be revealed (an availability check is fine) but it must never be a path back to the email. The weak point in "derive the default from the email local part" is exactly that: on a work or school domain, `johnsmith` plus the known domain is the email address, and usernames are known to link a person's accounts across services [1]. The GDPR makes the same point from another side: a handle is personal data (an online identifier, a pseudonym) [2] [3], and by default personal data must not be made accessible to an indefinite number of people without the person's own intervention [4]. The resolution that keeps the product's design: generate the default from the local part, but do not publish it until the user has seen it once on a first-run screen that says where it came from and offers a one-tap random alternative. Accepting the default is a single tap, so the step stays cheap.

The rest is engineering. Suffixes `name`, `name1`, `name2`… are fine and readable; their privacy cost is small (they reveal rank order of sign-up among same-base names), and they can be allocated in one indexed range query instead of probing. References to a user anywhere in the platform should store the opaque user id and render the handle at read time, which makes renames and deletion clean (the AT Protocol's DID/handle split is the model [5]).

## Recommendations (implementable rules)

1. **Default base from the email.** Take the local part (text before the last `@`); cut at the first `+` (sub-addressing, RFC 5233 [6]); NFKC-normalise; transliterate to ASCII with `anyascii` (ISC licence [7]), not `unidecode` (GPLv2+ [8]); lowercase; drop dots, hyphens and every character outside the handle alphabet; collapse repeated `_`; strip leading and trailing `_`. Reason: these are the parts of an email that carry no identity (Gmail itself ignores dots [9]) and the licence of `unidecode` would contaminate a permissively licensed package.
2. **Length.** Truncate the base to `max_len - suffix_reserve` (for a 20-character handle, reserve 3 characters, so suffixes up to 999 never force re-truncation). If the base is shorter than `min_len`, all digits, reserved, or empty, fall back to `user` plus a random 6-digit suffix. Reason: a fallback of `user1`, `user2`… would collide constantly and is itself an enumeration of the user base.
3. **Reserved names.** Block role and system names (RFC 2142 mailbox names such as `postmaster`, `abuse`, `admin` [10]; a maintained list such as `shouldbee/reserved-usernames`, MIT [11]; plus every platform route segment and app name). Reason: a handle can become a URL segment or a mention, and `admin` from `admin@company.com` would read as staff.
4. **Collision suffix `name`, `name1`, `name2`, …, `name10`, `name11`.** Keep it (it is what the product wants and it reads well). If the base ends in a digit, insert `_` before the suffix (`agent007` → `agent007_1`) so the suffix stays unambiguous. Do not use the birth year or account year: it discloses age-related data the platform otherwise would not publish (reasoning, not a sourced rule).
5. **Allocate in O(1) round trips.** One query on the unique index over the canonical handle: all rows in the range `[base, base || '\x7f')` matching `^base_?\d*$`; compute the smallest free `n` in memory; `INSERT … ON CONFLICT DO NOTHING` and retry with the next `n` if a concurrent sign-up won [12]. If more than a threshold (say 100) rows share the base, switch to a random 4-digit suffix. Prefix range scans need a B-tree index usable for prefix matching (`text_pattern_ops` or C collation in PostgreSQL [13]).
6. **First run.** Right after email verification and before the first app opens, one screen: the prefilled handle, a live preview `@handle`, the sentence "Other people see this name. It was made from your email address", a primary button "Continue as @handle", a secondary "Suggest another" (random) and an editable field. Until this screen is passed, the handle is not shown to other users. Reason: Art. 25(2) GDPR [4] and the email-linkage risk [1].
7. **Availability check.** Debounce 300–400 ms after the last keystroke, only once the input passes local syntax checks; cancel in-flight requests and drop stale responses; four states (checking, available, taken, invalid with reason); up to three suggestions when taken; a persistent `role="status"` region for results; `aria-invalid` plus `aria-describedby` on the field; icon and text, never colour alone. The server re-checks on submit and its unique constraint is the only authority.
8. **Endpoint.** `GET /handles/{handle}/availability` for authenticated, email-verified sessions only, rate-limited per account and per IP, rejecting any input containing `@`. It returns `{status, reason, canonical, suggestions}`; `reserved` and `quarantined` both come back as `unavailable`, so the endpoint does not reveal deleted accounts.
9. **Public representation.** Every API that apps call to render "by @handle" returns `{user_id, handle, display_name}` from a dedicated public-profile schema, never the account record. A test asserts that no public payload contains `@`-bearing email strings. Reason: OWASP API3:2023 (avoid generic serialisation, return the minimum fields, validate responses against a schema) [14].
10. **Renames and deletion.** Store references by user id; render handles at read time. On rename or deletion, quarantine the old canonical handle (90 days is GitHub's figure for deleted accounts [15]); keep only a keyed hash of the canonical handle in the quarantine list, with no link to the account. Content by a deleted user renders as "deleted user", not the old handle.

## 1. Generating the default handle

**Sub-addressing.** RFC 5233 defines the `user+detail` form for Sieve, where the separator is configurable but `+` is the common default [6]. The `+tag` is chosen by the user per service and is often the service's own name, so it should never reach a public handle. Only `+` should be treated as a separator: some providers use `-` or `.`, but stripping at those would cut real names (`jean-pierre`).

**Dots.** Gmail delivers `john.smith@gmail.com` and `johnsmith@gmail.com` to the same inbox, while dots in work or school accounts on Google Workspace are significant [9]. Dropping dots in the default therefore loses nothing for Gmail users and avoids the visual near-duplicates `john.smith` and `johnsmith` if the handle alphabet allows dots. If the platform's canonical form keeps dots as significant, keep this consistent with the other half of the specification.

**Transliteration and licences.** `Unidecode` is GPLv2+, its author says it is context-free character-by-character mapping whose quality falls "the further the script you are transliterating is from Latin", warns that some transliterations may offend, and advises against using it for strings directly visible to users [8]. `text-unidecode` is a port offered under Artistic or GPL licences, with the note that `unidecode` has better quality [16]. `anyascii` is ISC-licensed and covers "practically all Unicode characters", also character by character [7]. ICU's `Any-Latin; Latin-ASCII` compound transform converts "as much as possible to an ASCII-range representation" [17]; PyICU is MIT-licensed but needs the ICU C++ library installed [18], and ICU ships under the permissive Unicode License (SPDX `Unicode-3.0` in recent copies; I did not confirm from which ICU release) [19]. Recommendation: `anyascii` as the default (no system dependency, permissive), with ICU as a seam for deployments that already ship it. Whatever the engine, the user sees and can edit the result before it is published, which handles the "offensive transliteration" case.

**Too short, empty, reserved.** Local parts such as `j`, `42`, `info` or `contact` produce bad handles. Role names are standardised in RFC 2142 (`postmaster`, `abuse`, `hostmaster`, `webmaster`, …) [10], and community lists of reserved usernames exist to avoid URL collisions with resource paths [11]. A shared mailbox local part (`info@`, `sales@`) is a sign that the account is a role account, so falling back to `user` plus random digits is better than handing out `info`.

**Collision suffix: sequential vs random vs year.** Sequential suffixes are what the product asked for and what most people expect; Instagram's own advice when a name is taken is to add periods, numbers, underscores or abbreviations (seen in a search snippet of its help page; the page did not render for verification) [20]. Their privacy cost: `john7` tells observers that six earlier `john*` handles exist and that this account came later, which is minor because the handles are public anyway. Random suffixes (`john4821`) hide sign-up order and make bulk guessing of handles harder, at a readability cost. Year digits (`john1987`) publish an age-related fact the platform did not ask to publish; avoid them. Use sequential by default and random only as the overflow path (rule 5).

**Does the default leak the email?** Yes, partly, and the leak is the worst on corporate domains with `first.last` conventions, where handle plus domain reconstructs the address. Perito et al. showed that a significant share of profiles across services can be linked from usernames alone, and that people reuse a small set of related usernames [1]; an email local part is exactly such a reused string. I found no platform documentation describing a warning at first run for this specific case, so the recommendation (rule 6) is a design inference from the GDPR default rule [4] and from the linkage research, not an observed industry practice. OWASP recommends that users be allowed to use their email as a login but also be able to choose a username other than the email [21], which supports separating the two.

**Cost of probing.** Naive probing (`name`, then `name1`, then `name2`…) costs one round trip per collision and grows linearly with the popularity of the base. The range query in rule 5 returns every taken suffix of one base in one indexed read; the database's unique constraint plus `ON CONFLICT` handles the race between two sign-ups choosing the same `n` [12]. A per-base counter table (`base → next_n`, incremented atomically) is O(1) but leaves gaps when handles are later renamed or released and is one more piece of state to keep consistent; the range query is simpler and is enough at the scale where the overflow threshold kicks in.

## 2. The first-run "choose your username" step

**What real products do.** Discord moved in 2023 from `name#1234` to unique usernames because, by its account, nearly half of friend requests failed on a missing discriminator or wrong casing; new usernames are limited to lowercase `a–z`, `0–9`, `_` and `.`, and a separate, non-unique display name allows spaces, emoji and non-Latin scripts and by default was set to the old username without the discriminator [22]. Its help centre gives 2–32 characters and forbids two consecutive periods (from search snippets; the page returned HTTP 403 to my fetcher) [23]. The rollout was staged by priority: owners of partner and verified servers, then users by account age starting with 2015 registrations, with early access for some Nitro subscribers; numeric user ids did not change, and the old `name#1234` kept working as an alias [22]. Bots were assigned new usernames automatically [24]; I could not confirm what happened to humans who never chose one. GitHub suggests alternatives when a chosen name is taken ("adding a number, hyphen, or alternative spelling") in its rename flow [25]; I could not verify the exact text of its sign-up form. Threads takes the Instagram username and changes go through Instagram (third-party guide, no official page found) [26]. Bluesky gives every account a handle under `bsky.social` that can later be replaced by a domain the user owns; handles are case-insensitive, normalised to lowercase, and are mutable pointers to a permanent DID [5]. Slack keeps a required full name and an optional, non-unique display name with reserved words such as "here" and "you" [27]. Reddit reportedly assigns a random username to some sign-ups (Google or Apple) and lets the user change it once at first login; only secondary sources describe this [28]. Notion: I found no public-handle concept to report on.

**Pattern to adopt.** Two names, as Discord, Bluesky and Slack do: the unique handle (constrained alphabet, lowercase) and a free-form display name. That lets the handle stay short and non-identifying while people still show a real name where they want to.

**Skippable?** Yes, in the sense that "Continue as @handle" accepts the default with one tap. No, in the sense that the screen itself is shown once: the platform needs one moment of user intervention before publishing a name derived from the email [4]. Reddit's one-time change at first login (secondary sources) [28] is the same idea with less clarity.

**Placement.** After email verification (the handle needs an account to belong to) and before the first app renders the user anywhere. If a user reaches an app by deep link, the platform shell shows the step first and then continues to the target URL.

## 3. Availability check as you type

**Timing.** There is no standard debounce value. Nielsen's response-time limits are the useful frame: 0.1 s feels instantaneous, 1 s keeps the flow of thought [29]. A 300–400 ms debounce plus a fast endpoint puts the result well under 1 s after the user pauses. Smashing Magazine's review of live validation names "an available username" as one of the few cases where immediate feedback is worth it, and recommends a character threshold before validating [30]; Nielsen Norman Group calls errors shown before the user has committed to a mistake "premature" [31]. So: do not show "too short" while the user is still typing the first characters; show local syntax errors after the debounce only once the input has at least `min_len` characters or on blur; show "taken" only from a completed server response.

**States.** `checking` (spinner plus text, shown only if the request outlasts roughly 300 ms, so fast answers do not flicker), `available` (`@name is available`), `taken` (`@name is taken` plus up to three available suggestions as buttons), `invalid` with the specific rule (`Use only a–z, 0–9 and _`, `At least 3 characters`, `This name is reserved`). The client keeps a request sequence number and ignores responses older than the latest input; an `AbortController` cancels superseded fetches.

**Accessibility.** Status messages must be programmatically determinable without moving focus (WCAG 4.1.3) [32]; `role="status"` has an implicit `aria-live="polite"` [33]. The live region must exist in the DOM before text is injected into it, or screen readers may not announce it [32]. Colour cannot be the only signal (WCAG 1.4.1) [34], so each state has text and an icon. Set `aria-invalid="true"` only after validation has actually failed, and link the message with `aria-describedby` (technique ARIA21) [35]. Offering available alternatives when a name is taken is also what WCAG 3.3.3 Error Suggestion asks for when a correction is known [36].

**Race with submit.** The client result is advisory. On submit the server canonicalises again, checks reserved and quarantine lists, and inserts under the unique constraint; on conflict it returns the same `taken` payload with fresh suggestions, and the client moves focus to the field.

**Rate limiting and enumeration.** OWASP's guidance is to answer authentication flows generically so they do not reveal whether an account exists, and it names registration as a place where this applies [21]. A handle availability endpoint necessarily reveals that a handle exists; that is acceptable because handles are public, as long as the endpoint accepts only handles, never emails, and as long as the default handle is not a derivative of the email that was published without the user's choice (section 1). Apply a per-client rate limit as OWASP API4:2023 recommends, with stricter limits on sensitive endpoints [37]; restricting the endpoint to verified sessions makes bulk enumeration require bulk verified accounts.

**Normalisation preview.** Show the canonical form under the field as the user types (`Your handle will be @john_smith`), rather than rewriting the input value, which would move the caret. The preview must use the same canonicalisation function as the server (shared rules, or the endpoint's `canonical` field), which also covers the Unicode case folding and confusables policy covered in the other half (RFC 8265 UsernameCaseMapped [38], UTS #39 [39]).

## 4. Hiding the email; GDPR

**Is a handle personal data?** Yes. Art. 4(1) GDPR lists "an online identifier" among the things that make a person identifiable, and Art. 4(5) defines pseudonymisation as processing such that data can no longer be attributed to a specific person without additional information kept separately [2]. Recital 26 says pseudonymised data that could be attributed to a person with additional information should be considered information on an identifiable person [40]. The CNIL lists "pseudonyme" and "identifiant de connexion" among personal data and states that pseudonymised data remain personal data [3]. The EDPB's Guidelines 01/2025 on pseudonymisation (adopted 16 January 2025 for public consultation; I did not confirm a final version) say pseudonymised data stay personal data even when another party holds the additional information, and that pseudonymisation helps with data minimisation and data protection by design and by default [41]. The CJEU's EDPS v SRB judgment (C-413/23 P, 4 September 2025) adds nuance: pseudonymised data are not personal data "in all cases and for every person", but the controller's obligations are assessed from the controller's side, at collection [42]. For the platform, which holds the handle-to-email mapping, the handle is personal data, full stop. A handle the user chose themselves, unrelated to their name, is close to the ideal pseudonym; a handle derived from `first.last@company.com` is not much of one.

**Minimisation.** Art. 5(1)(c) requires data to be "adequate, relevant and limited to what is necessary" [43]. Apps that only need to show authorship need the user id and handle, never the email. Rule 9's dedicated public schema and the OWASP advice against generic serialisation [14] implement this; an app that genuinely needs to contact a user should go through a platform messaging API rather than receive the address.

**Privacy by default.** Art. 25(2): by default, personal data must not be made accessible without the individual's intervention to an indefinite number of natural persons [4]. Publishing an email-derived handle the moment an account is created is hard to square with this; the first-run screen is the intervention.

**Erasure.** Art. 17 gives a right to erasure, with exceptions including freedom of expression and information (17(3)(a)) [44]. On deletion: erase the account record and the handle's link to it; render the user's own content as "deleted user"; mentions in other users' content stay as text written by those users, but if mentions are stored as user ids (rule 10), they render as "deleted user" too, which removes the handle from the live platform without editing anyone else's words. Handle reuse is a separate question. GitHub releases a deleted account's username after 90 days, but permanently retires owner/repository name pairs that had significant use [15]; Mastodon makes a deleted username unavailable on that server forever [45]; Codeberg users have reported impersonation risk from reusable names of deleted users [46]. A quarantine list that stores only a keyed hash of the canonical handle, with no account link and a fixed expiry, is a defensible middle ground: it serves the platform's legitimate interest in preventing impersonation and keeps little personal data. Whether such a hash is still personal data is a case-by-case question after SRB [42]; treat it as personal data and document the retention period.

**Rectification and renames.** Art. 16 is a right to have inaccurate data corrected [47]; a handle a user chose is not "inaccurate", so renames are a product choice rather than a legal duty. Allow them with a rate limit (Discord: "not too often" [22]) and the same quarantine as deletion. GitHub's documentation shows what goes wrong when references are stored as strings: after a rename the old profile URL returns 404, @mentions of the old name are not redirected, and the old name becomes available for anyone to claim [48]. Storing ids and rendering handles at read time avoids all three.
