enlace_auth.handles#

Handles (usernames): the public, unique, case-insensitive name of an account.

The email stays the account’s private key; the handle is what other people and apps see (“by @thorwhalen”). Three layers, imported one way:

  • core: the rules (normal form, validity, reserved names, the default from an email, suggestions). Pure; no web or storage imports.

  • registry: HandleRegistry, which account holds which handle, over two MutableMapping s, unique under a lock.

  • directory: HandleDirectory, the read-only view every app gets at request.state.handles (set by HandleDirectoryMiddleware).

  • routes: /auth/handles/* for the browser.

An app’s server shows “by <handle>” with request.state.handles.handle_of(owner), where owner is the request.state.user_id it stored; it never sends emails to the browser. See misc/docs/research/general/usernames.md for the rules’ sources.

Look handles up by account and accounts up by handle; nothing else.

Only confirmed handles: an account that has not yet confirmed its default (made from its email) has none to show, and handle_of returns None. An app then shows no name, or sends its user to its “choose your username” step.

This is a convenience for trusted server code, not a boundary between apps: every app server on the platform runs in the platform’s process and already sees its own users’ emails. What must never happen is an email reaching a browser; that is the app’s duty, and this view makes it easy by dealing in handles.

Bases: object

Handles of accounts: assign defaults, claim, rename, release, look up.

A default handle (made from the email) is private until its account confirms or changes it: it lives only in the account’s own owners record, never in handles. So lookups, the availability check, timings and other accounts’ defaults are all unaffected by it, two accounts may hold the same private default, and confirming one is an ordinary claim that can find the name taken. A handle made from an email gives part of the address away, so it is published only by its owner’s own action (GDPR Art. 25(2); see misc/docs/research/general/usernames.md).

Parameters:

  • handles (MutableMapping) – uniqueness key -> public name entry (see the module docstring)

  • owners (MutableMapping) – account -> its handle record

  • policy (HandlePolicy) – the rules (HandlePolicy)

  • lock (Optional[Callable[[], ContextManager]]) – a zero-argument factory of a context manager held around writes

  • account_exists (Callable[[str], bool]) – whether an account exists; checked under the lock, so nothing is written for an account deleted meanwhile

  • quarantine_seconds (float) – how long a released public name stays out of others’ reach (a renamed one redirects meanwhile)

  • rename_cooldown_seconds (float) – the least time between two public names (the first choice is free)

  • clock (Callable[[], float]) – the time, in epoch seconds

claim(account, wanted, *, force=False)[source]#

Publish wanted as account’s handle (also: confirm its default).

The first public name is free; changing it waits rename_cooldown_seconds after the last change, and the old name stays with the account for the quarantine (it redirects). force (an admin) skips the reserved list, the cooldown and a quarantine, never a public owner. Raises HandleError; a taken one carries suggestions.

release_account(account)[source]#

Forget account’s handles (the account is being deleted); return 1 or 0.

Its public name, and the names it renamed away from, stay out of others’ reach for the quarantine with no account attached (the email is erased); then they are free. Only entries that name this account are touched, and the record goes last, so an interrupted release never frees a name early.

Return type:

resolve(handle)[source]#

{"handle": current} for handle, following a recent rename.

A name its account renamed away from, still in quarantine, resolves to that account’s current handle with "renamed_from"; a deleted account’s name, a private default, or an unknown one resolves to None.

>>> reg = HandleRegistry({}, {}, account_exists=lambda a: True)

The base of a default handle: the email’s local part, made into a handle.

The +tag of plus-addressing is dropped (it is private routing, and often names the site), accents are folded, other characters removed, separator runs collapsed, and the result cut so a suffix still fits. When nothing usable is left, or the local part is a reserved word (info@, admin@: role mailboxes), policy.fallback_base. The base may still be too short: candidates() then starts at the first suffix.

>>> base_from_email("José.Ñúñez@example.com")
'jose.nunez'
>>> base_from_email("o'brien@example.com")
'obrien'
>>> base_from_email("--@example.com"), base_from_email("info@example.com")
('user', 'user')

Valid handles to try, in order: base, base1 .. base<max_sequential>, then base plus a random number of policy.random_suffix_digits digits. Endless unless tries bounds the names generated (valid or not): a caller that must terminate passes it.

Invalid ones (too short, reserved) are skipped, so bo starts at bo1. The base is cut so the suffix fits. Sequential suffixes are what people expect (the first john is john, the next john1); the random tail keeps a crowded base from costing a hundred lookups.

>>> list(candidates("thorwhalen", limit=3))
['thorwhalen', 'thorwhalen1', 'thorwhalen2']
>>> list(candidates("agent007", limit=2))
['agent007', 'agent007_1']
>>> no_sequence = HandlePolicy(max_sequential=0)
>>> list(candidates("xyz", policy=no_sequence, rng=lambda a, b: 424242, limit=2))
['xyz', 'xyz424242']

The form two handles are compared by: normalised, without separators, with look-alike characters folded (0 as o; 1 and i as l).
