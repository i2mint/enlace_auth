enlace_auth.handles.core#

What a handle is: its normal form, its rules, and the default made from an email.

A handle (a username) is the public name of an account: unique, case-insensitive, shown as @name. The account itself stays keyed by its email, which no other user and no browser of another user ever sees. This module is pure (no web, no storage imports), so the rules can move unchanged; registry.py holds the state.

The rules, and why (the research behind each is in misc/docs/research/general/usernames.md):

  • ASCII only: lowercase a-z, digits, and the separators ., _, -. Input is NFKC-normalised and case-folded first, so ThorWhalen and fullwidth ｔｈｏｒ are accepted and stored as thorwhalen / thor. Restricting the stored form to ASCII removes the Unicode confusables problem (UTS #39) instead of detecting it.

  • Case-insensitive by construction: the stored form is lowercase, so the display form and the comparison form are the same string.

  • Separators and look-alikes do not distinguish: john.smith, john_smith, johnsmith and j0hnsmith have one uniqueness_key(), so a name cannot be impersonated by moving a dot or swapping o for 0. A separator may not start or end a handle, nor follow another one (so a trailing dot is never swallowed as punctuation after @name.).

  • Not all digits: an all-digit handle reads as an id.

  • Reserved words (RESERVED): routes, roles and system words that would let an account pass for the platform. A host adds its own (its group names).

>>> normalize("@ThorWhalen ")
'thorwhalen'
>>> handle_problem("thorwhalen") is None
True
>>> handle_problem("thor..whalen")
'A dot, dash or underscore cannot follow another one.'
>>> {uniqueness_key(h) for h in ("john.smith", "john_smith", "j0hnsmith")}
{'johnsmlth'}
>>> base_from_email("John.Smith+news@example.com")
'john.smith'
>>> list(candidates("bo", limit=3))
['bo1', 'bo2', 'bo3']

The base of a default handle: the email’s local part, made into a handle.

The +tag of plus-addressing is dropped (it is private routing, and often names the site), accents are folded, other characters removed, separator runs collapsed, and the result cut so a suffix still fits. When nothing usable is left, or the local part is a reserved word (info@, admin@: role mailboxes), policy.fallback_base. The base may still be too short: candidates() then starts at the first suffix.

>>> base_from_email("José.Ñúñez@example.com")
'jose.nunez'
>>> base_from_email("o'brien@example.com")
'obrien'
>>> base_from_email("--@example.com"), base_from_email("info@example.com")
('user', 'user')

Valid handles to try, in order: base, base1 .. base<max_sequential>, then base plus a random number of policy.random_suffix_digits digits. Endless unless tries bounds the names generated (valid or not): a caller that must terminate passes it.

Invalid ones (too short, reserved) are skipped, so bo starts at bo1. The base is cut so the suffix fits. Sequential suffixes are what people expect (the first john is john, the next john1); the random tail keeps a crowded base from costing a hundred lookups.

>>> list(candidates("thorwhalen", limit=3))
['thorwhalen', 'thorwhalen1', 'thorwhalen2']
>>> list(candidates("agent007", limit=2))
['agent007', 'agent007_1']
>>> no_sequence = HandlePolicy(max_sequential=0)
>>> list(candidates("xyz", policy=no_sequence, rng=lambda a, b: 424242, limit=2))
['xyz', 'xyz424242']

Up to n free handles close to wanted, for a name that is taken or invalid.

wanted is first made into a base the way an email’s local part is, so Thor Whalen! suggests thorwhalen1 and so on.

>>> suggestions("ThorWhalen", lambda h: h not in taken)

enlace_auth.handles.core.uniqueness_key(handle)[source]#

The form two handles are compared by: normalised, without separators, with look-alike characters folded (0 as o; 1 and i as l).

So th0r.whalen cannot pose as thorwhalen. It is a key, never shown.

>>> uniqueness_key("@Thor.Whalen") == uniqueness_key("th0r-whalen")
True
>>> uniqueness_key("bill") == uniqueness_key("b1ll")
True
