enlace_auth.signup.routes#

/auth/email/*, the verify-first /auth/register, and self-service deletion.

Verify before create. No user record is written until the address has proved it receives mail: start mails a one-time code, verify spends it and then signs in an existing account or creates the new one. That closes the two gaps of a register-then-verify flow: answering whether an address has an account (enumeration), and an attacker creating an account for a victim’s address before the victim does (pre-hijacking).

The code is bound to the browser that asked for it. start sets an HttpOnly cookie holding a fresh random nonce, the pending code is stored under it, and verify finds the code only through that cookie (refused when the request carries it twice). Only the newest code of a browser works. So a sign-up is finished by the browser that began it: nobody can register a victim’s address with their own password and wait for the victim to verify it, and nobody can sign a victim’s browser into an account of theirs by sending a link. A stranger asking for codes for an address replaces only their own pending code, never the owner’s.

start answers every address the same way, byte for byte, and does the same work for each: it always stores a pending code (a decoy that can never verify for an address the policy refuses, or for an admin account) and always mails in the background. Only the mail differs: a code, or a short “sign-up here is by invitation” notice. A submission failing the bot check gets the same answer and no mail. Rate limits answer 429; they count hits, not accounts.

Endpoints, all CSRF-checked like every other /auth POST:

  • GET  /auth/email/challenge a bot-check token for an API client’s form

  • POST /auth/email/start {email, app?, next?, lang?, challenge, website}

  • POST /auth/email/verify {email, code} or {token} (the emailed link)

  • GET  /auth/email/link the link’s landing page (token in the fragment)

  • POST /auth/register {email, password, ...}: start that also sets a password on the account it creates

  • POST /auth/account/delete/start mails the signed-in account a confirmation code

  • POST /auth/account/delete {code}: deletes it

enlace_auth.signup.routes.make_limit_gates(rate_limiter, limits=None)[source]#

(mail_allowed, verify_allowed), each (email, client_ip) -> bool.

mail_allowed (kind= signin, reset or delete) charges the address, the IP and the overall budget of that kind of mail, so flooding one kind cannot stop the others. verify_allowed charges the address-and-IP pair, the IP, and the overall budget of code checks: keyed on the pair, so a stranger’s wrong guesses do not lock the owner out, and the overall budget bounds how many guesses all clients together get. Every key is charged even after one is over, or a client at one cap would stop counting against the others.

>>> mail, _ = make_limit_gates(SlidingWindowLimiter({}), {"mail_per_address": 1})
>>> mail("a@x.io", "1.2.3.4"), mail("a@x.io", "5.6.7.8"), mail("b@x.io", "5.6.7.8")
(True, False, True)
>>> mail("a@x.io", "1.2.3.4", kind="reset")
True

Build the sign-up router. See the module docstring for the endpoints.

Parameters:

  • session_store (user_store /) – the platform’s account records and sessions.

  • signing_key (str) – HMAC key for codes, link tokens, challenges and cookies.

  • send_email (EmailSender) – delivers the mails (to=, subject=, body=; never raises).

  • policy (Optional[SignupPolicy]) – who may create an account from which app (default: nobody); its admin addresses are never created and get no sign-in codes.

  • codes (Optional[PendingCodes]) – the pending-code store (default: in memory, 10 minutes, 5 tries).

  • rate_limiter (Optional[RateLimiter]) – allow(key, *, limit, window) (default: in memory).

  • bot_check (Optional[BotCheck]) – challenge() / verify(fields) (default: honeypot plus a 2-second time-to-submit).

  • limits (Optional[dict]) – the counts of SignupLimitsConfig as a dict.

  • client_ip (Callable[[Request], str]) – (request) -> str, the client a rate limit counts (the plugin reads X-Forwarded-For only from a trusted proxy).

  • known_apps (Iterable[str]) – app names a sign-up may name, directly or through next.

  • delete_account (Optional[Callable[[str], None]]) – delete(email), removing an account and its data; None leaves the deletion endpoints unmounted.

  • public_base_url (Optional[str]) – the origin put in mailed links. Without it the link is built from the request’s Host, which the requester controls.

  • terms_version (Optional[str]) – stored on each account created, as the terms accepted.
